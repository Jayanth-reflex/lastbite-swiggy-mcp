Last Bite v2 — from a food bot to a model-agnostic Swiggy agent

v1 is a single-tenant, food-only web bot reached through a Claude-Desktop token hack, with the model hard-wired. v2 is a cloud-first, multi-tenant, multi-model chat app that connects to all three Swiggy MCP surfaces over native OAuth, remembers your conversations, and lets you save prompt-workflows that run on a trigger — with one non-negotiable invariant carried over and generalized: no irreversible order ever fires without passing a spending gate.

The thesis. Using Swiggy MCP inside Claude/ChatGPT gives you one model, one session, no memory of your routines, and no automation. Last Bite v2's wedge is exactly those gaps: persistent threads + your choice of model + saved workflows that trigger themselves — wrapped in a safety layer those generic apps don't have for irreversible COD spend.

This document is the high-level design for your review. Diagrams and component contracts below. Nothing is built yet — once you approve, I write the spec + an implementation plan.

~35 tools total. The 3 bold tools are the only ones that commit/spend — the gate wraps exactly those.

Hard constraints (non-negotiable)

  • OAuth 2.1 + PKCE per user; bearer = identity, auth auto-handled.
  • COD only · orders cannot be cancelled. Food cart < ₹1000 (beta). Dineout = free bookings only.
  • No webhooks · no idempotency guarantee · no rate-limit doc. Tracking = poll-only.
  • "Keep the Swiggy app closed" — session conflict.
  • Prod for a 3rd-party webapp is approval-gated (localhost dev is open; submit video for prod creds).

Two data stores by intent: Supabase Postgres = durable, relational, RLS-isolated (the system of record incl. encrypted tokens); Upstash Redis = ephemeral safety primitives that need sub-ms atomic ops (locks, grace, idempotency). QStash drives anything time-based.

Why the gate sits in layer 4, not the prompt. Any model in layer 3, reached from any channel in layer 1, can emit a place_food_order tool call. If the gate lived in a system prompt, a different model or a jailbreak could skip it. Putting it in the MCP proxy — below the model — means the spend tools are physically un-callable without passing it. This is the single most important structural decision in v2.

04★ The Spending Gate (generalized 7-layer model)

v1's safety lived inside a rigid LangGraph pipeline. v2 lifts it into a tool-call interceptor in the MCP proxy so it works for an open tool-calling loop, any model, and any channel — sync or async. Read-only tools (search_*, get_*, track_*) pass straight through. The three commit tools are intercepted.

model emits tool call ──▶ GuardedMcpProxy.call(tool, args, ctx)
                              │
        is it a SPEND tool?   │  place_food_order · checkout · book_table
         ┌──────────no────────┴───────────yes──────────┐
         ▼                                              ▼
  execute on Swiggy MCP                      SPENDING GATE
  (read-only / cart ops)              L1 kill-switch  LB_REAL_ORDERS=1 ? else → demo result
                                      L2 user mode    connection.mode == live ? (default demo)
                                      L3 guardrails   cart < ₹1000 · COD · dineout=free · surface caps
                                      L4 CONFIRM      emit pending_action; DO NOT execute yet
                                                    ├─ sync (chat):  UI renders gate card → user YES
                                                    └─ async (cron): notify → user YES within window
                                      L5 grace        30s STOP window after YES (cancellable)
                                      L6 idempotency  SETNX sha256(user·cart·day) — dup → no-op
                                      L7 mutex+audit   per-user lock; append immutable audit row
                                              │ all pass
                                              ▼
                                      execute place/checkout/book on Swiggy MCP
                                              ▼
                                      audit: placed · idempotency held 24h · notify result

What's new vs v1

  • + Interceptor, not pipeline — works for any model's tool loop.
  • + Async confirm path — pending_action row + notify + resume on YES (the D2 decision). Same gate, delivered over time.
  • + Generalized to 3 surfaces — checkout & book_table get the same treatment as place_food_order.
  • + Immutable audit log in Supabase — every gate evaluation + outcome, joinable by request-id.

What's preserved from v1

  • = Two-layer kill switch (env + per-user mode, default demo).
  • = 30s grace + 5-failure circuit breaker (Redis blip → cancel, never commit).
  • = sha256(user·cart·day) idempotency, release-on-transient-failure.
  • = Per-user mutex (TTL > function budget), abandoned-thread auto-clear.

Async-confirm safety rule (D2). A scheduled workflow can prepare a cart and ask, but the gate's L4 still requires a real human YES — delivered via WhatsApp/push/email — before L5–L7 run. If no YES arrives inside the window, the pending_action expires and nothing is placed. There is no "silent auto-spend" path in v1 scope.

05Multi-model gateway (D1)

Design

  • One interface: Vercel AI Gateway with creator/model strings (OpenClaw-style), e.g. anthropic/claude-…, google/gemini-…, xai/grok-…, deepseek/….
  • Full OpenClaw-style catalog (D8): also OpenAI, Mistral, Groq, and OpenRouter as a meta-provider for the long tail. A curated default list + dynamic fetch; one picker, grouped by provider.
  • Operator keys, server-side. You supply provider keys; stored as Vercel env / Gateway config — never in the browser. Users only choose a label.
  • Failover (OpenClaw pattern): primary + fallback per role; retry only on 429/quota, not on tool errors.
  • Model policy by thread type: a thread that may call Swiggy tools is pinned to a tool-reliable model; a plain Q&A thread can use any.
  • Spend observability from the Gateway feeds the audit/ops view.

Key handling (LibreChat-informed)

  • v1: operator keys only — simplest, you fund it, users just pick.
  • v2 (optional) BYOK: if users bring their own provider key, store it AES-encrypted in Supabase (app key + per-row IV), decrypt only at call time. Mirrors LibreChat's CREDS_KEY/CREDS_IV.

Tool-call caveat (verified in research): some models (notably Gemini via certain gateways) drop large tool-call blocks. We verify each model's MCP tool-calling in CI and mark non-passing models "chat-only" in the picker.

06Auth & token vault (D3)

Two distinct identities

  • App identity — Supabase Auth (email / Google OAuth). Issues the session; every API call resolves a user_id.
  • Swiggy identity — separate per-user OAuth 2.1 + PKCE connection to Swiggy MCP. A user logs into Last Bite, then "Connect Swiggy" once.
  • The two are linked in swiggy_connections(user_id → encrypted token, scopes, expiry).

Token vault

  • At rest: AES-256-GCM, app key from secret manager, per-row IV+salt, in Supabase. RLS so a row is only readable by its owner's authenticated context.
  • Decrypt only inside SwiggyClient construction, server-side. Never to the client, never logged.
  • Refresh: use the refresh_token; on 401 from Swiggy, attempt refresh once, else mark connection stale → prompt reconnect.
  • Redaction middleware (kept from v1) strips Bearer ey… / JWT shapes from every log + error.

This replaces the v1 BYOC / Claude-Desktop token-paste entirely. The PKCE + dynamic-client-registration code already in lib/swiggy-oauth.ts is resurrected as the primary connect flow — for dev it runs against http://localhost (Swiggy allows this with no approval); for prod we submit the Builders Club application.

07Chat system (ChatGPT/Claude-style)

Threads

Left rail lists past conversations; new-chat; rename/delete. Each thread pins a model + (optional) a Swiggy surface scope.

Memory / context

Full message history persisted in Supabase; the turn loads a rolling window (+ summary of older turns) so the model has continuity. Tool calls + results are part of the transcript.

Turn loop

Streaming tool-calling loop: model ↔ Guarded MCP proxy until no more tool calls, then final answer streams. Spend tools surface a gate card inline.

Memory is scoped per user_id and per thread_id with RLS — one user's threads are invisible to another, enforced at the database, not just the app.

08Workflow engine — the differentiator

A workflow = a saved natural-language instruction + a trigger + a confirm policy. When the trigger fires, the engine runs the instruction through the same agent loop and Guarded MCP proxy as interactive chat — so all safety applies identically.

Anatomy

workflow {
  name:      "Friday dinner — my usual"
  trigger:   { type: cron, expr: "0 20 * * 5", tz: "Asia/Kolkata" }
              | { type: manual } | { type: keyword, on: "restock" }
  prompt:    "Order 1 Paradise chicken biryani to Home,
              best coupon, under ₹600."
  surface:   food            // food | instamart | dineout
  confirm:   async           // D2: notify, place only on YES
  window:    30m             // YES must arrive within
}

Trigger types (v1)

  • Manual — "run now" button.
  • Scheduled — QStash cron (the headline: "every Friday 8pm…").
  • Keyword — a phrase in chat/WhatsApp runs a saved workflow.

Run lifecycle

QStash fires → workflow_runs row (queued) → agent builds cart → Spending Gate L4 emits pending_action + notify → user YES → place → run = done. No YES in window → run = expired, nothing placed.

"Restock when low" — honest scoping. Swiggy MCP exposes no pantry/inventory signal, so true depletion prediction isn't possible from MCP data alone. v1 models it as scheduled cadence ("every 10 days") or a user-declared "we're out of X" keyword trigger — not a magic sensor. The predictive Poisson model is a later, opt-in addition, clearly labeled as an estimate.

09WhatsApp channel (D4 · Gupshup, notify + trigger)

Role

  • Outbound: async-confirm prompts ("Cart ready ₹540, reply YES in 30 min"), order-placed receipts, tracking nudges.
  • Inbound: YES/STOP to resolve a pending_action; keyword to trigger a saved workflow.
  • Number is linked to the account during onboarding (so inbound maps to a user_id).

Compliance (built in)

  • 24-hour session window — free-form replies only after the user messages us; outside it requires pre-approved templates (utility category for confirms).
  • Webhook signature/secret, fail-closed in prod (kept from v1, verified → 403).
  • Inbound dedup by message-id (msg: key). YES is just another route into the Spending Gate L4 resume.
  • ✗ No Baileys/unofficial bridges — ban risk, never gate COD on them.

13Flow · scheduled auto-order (async confirm — D2)

QStash cron Fri 20:00 IST ─▶ workflow_runs(queued) ─▶ runner loads saved prompt + user's Swiggy token
  ▼ agent builds cart (read/cart tools, pass-through)
  ▼ model calls checkout/place  →  GATE L1·L2·L3 pass
  L4 confirm = async:  write pending_action(cart, expires=+30m)
                          notify via WhatsApp template: "Your Friday usual: ₹540. Reply YES in 30 min, or STOP."
  ┌───────────────── user replies within 30m ─────────────────┐
  │  YES → resume gate L5 grace → L6 idem → L7 → place ✓ notify receipt
  │  STOP → pending_action=cancelled, run=cancelled, notify
  └─ no reply → pending_action expires → run=expired → nothing placed (notify "skipped")

Same gate, same audit trail — only L4's delivery is deferred. No code path places without a human YES.

17Open items & risks

Risks / watch-items

  • Prod approval is Swiggy-gated. Full public launch waits on Builders Club creds — build now on localhost/preview against live MCP.
  • Per-model tool-calling varies. Verify each model's MCP function-calling; mark failures chat-only.
  • No Swiggy webhooks. Tracking is polling — cost/latency managed via QStash backoff.
  • WhatsApp templates need Meta approval — lead time before P5 confirms can ship.
  • "Keep Swiggy app closed" session conflict — surface as user guidance.

Questions still open for you

  • Households (direction D) — in P4 scope, or after? (Adds shared-workflow + member roles.)
  • Email provider for notifications (Resend?) — confirm before P4.
  • Confirm-channel priority for scheduled orders (web push / email / WhatsApp) — and require ≥1 before a schedule can arm.
