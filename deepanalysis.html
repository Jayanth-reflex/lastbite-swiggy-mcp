Last Bite — a regret-proof Swiggy ordering agent

A single-tenant Next.js 16 web agent that takes a natural-language food order (“chocolate ice cream within 7km of MyHome, best rated, under ₹300”), resolves it against Swiggy’s official MCP server, and walks it through a multi-stage human-in-the-loop confirmation before placing a COD-only, non-cancellable order. The entire reason the project exists is one upstream fact: Swiggy MCP orders cannot be undone — so the product’s real surface area is not the ordering, it’s the not-ordering-by-accident.

What stands out. This is not a weekend demo wearing a safety costume. It carries a written safety contract (docs/SAFETY.md), a self-audit that names 18 silent-failure paths with commit references (docs/AUDIT_2026-05.md), typed error taxonomies at every I/O boundary, and a regression test that exists specifically because a real ₹321 order once fired on a bug. The engineering maturity is well above the “portfolio project” baseline.

The honest catch. It is a developer beta, not a consumer product. Swiggy’s MCP auth server added a client whitelist (~2026-05-07) that rejects the app’s hosted redirect URI (issue #53), so every user must run Claude Desktop, complete Swiggy OTP there, dig the bearer token out of Claude’s local data, and paste it into /connect (BYOC = “bring your own Claude”). Real orders are double-gated off by default. And the headline “30-second countdown, type STOP to cancel” is fully wired only on the unprovisioned WhatsApp surface — see finding F1.

Below: an independent read of the architecture, the safety model verified against the actual code, and a calibrated list of gaps — including a few that the project’s own May audit didn’t catch.

01What this actually is

The repository root CLAUDE.md describes an ambitious five-project portfolio on Swiggy MCP (Last Bite → Trail → ChaiCal → Bharat Pantry → Saans). The code on disk is Project 1 only. Everything else is roadmap — and the docs are refreshingly explicit about that (docs/ARCHITECTURE.md §“Things this doc deliberately omits”).

What is built & shipped

  • ✓ Web chat at /order/new (demo + live modes)
  • ✓ BYOC token-paste onboarding at /connect with Redis-encrypted storage
  • ✓ LangGraph supervisor: Searcher → Recommender → Confirmer → Placer
  • ✓ Three confirmation gates + 30s grace + idempotency + per-user mutex
  • ✓ AI intent extraction + deterministic filtering + near-miss recommendations
  • ✓ Expired-token self-heal (Swiggy 401 → wipe → re-connect)
  • ✓ DPDP-aligned /privacy, redaction middleware, request-id correlation

Wired but not live / roadmap

  • ◐ WhatsApp inbound (/api/whatsapp) — fully coded, Gupshup not provisioned in prod
  • ◐ Native OAuth + PKCE + RFC 7591 DCR — works, but parked behind Swiggy’s whitelist (issue #53)
  • ✗ Trail, ChaiCal, Bharat Pantry, Saans — not in this repo
  • ✗ Live order tracking UI (depends on Project 2)

The OAuth machinery is kept intact so re-enabling native sign-in is “a one-line UI swap” the day the whitelist clears.

Design center of gravity. The interesting code is concentrated in three places: the agent graph (lib/agent/graph.ts, 790 lines — the single biggest file), the BYOC token bridge (lib/byoc.ts + lib/crypto.ts + lib/session.ts), and the safety primitives (lib/redis.ts + lib/user-prefs.ts). Everything else is conventional shadcn-on-Next.js.

Notable stack discipline: the only LLM call in the ordering path is intent parsing. Filtering, sorting, address resolution, cart parsing and the entire safety machine are deterministic TypeScript — not an agentic tool loop. This is the right call for a system that spends real money.

03Request flow

One chat message = one agent turn. The route reads the session cookie, fetches the user’s decrypted BYOC token, constructs a per-user SwiggyClient, and drives exactly one turn through the graph under a per-user lock.

Mirror path: app/api/whatsapp/route.ts drives the same processTurn() from Gupshup inbound — with one critical difference in how it handles the grace window (see F1).

04The agent graph

A LangGraph StateGraph over a typed LastBiteState (lib/agent/graph.ts:34). The cleverness is in the reducers and the routing, not in LLM autonomy.

Searcher — deterministic by design

One Groq call (parseIntent) yields a Zod-validated Intent with a hard “NEVER FABRICATE” system prompt — null means “user didn’t say it”, which downstream filters respect (lib/agent/intent.ts:55). Then pure TS: applyHardFilters (rating, distance, veg, name), sortByQuality, probe the top-3 menus, first clean cart wins (graph.ts:143–206, 522–560). Cart parsing is permissive over ~6 field-name conventions (lib/agent/tools.ts:tryParseCart).

Recommender — the “no silent fail” node

When nothing meets every constraint, instead of a dead end it returns the closest near-misses with annotated reasons — “8km away (>5km cap)”, “4.0★ (asked ≥4.5★)” — and lets the user pick a number (graph.ts:126–141, 563–612). This node exists because no-match “used to fail silently”.

Confirmer — gates 1 & 2

Calorie then ETA, each via LangGraph interrupt(): the graph pauses, the route returns the prompt, the next turn resumes on the reply. Anything not classifiable as YES re-prompts; STOP cancels (graph.ts:614–637, classifyReply handles Hinglish: haan/nahi/ruko).

Placer — where money is spent

Final gate → startGraceTimer + awaitGrace(30s) → consumeIdempotency → effectiveMode two-layer guard → real place_food_order or a demo_ id (graph.ts:639–740). Order-id extraction parses both plain-text and JSON confirmations.

Two state-machine bugs already fixed, with the scar tissue documented in-code.

① The gatesPassed reducer is replace, not merge — a merge leaked passed gates from a prior terminal run into the next order on the same thread_id, which would have skipped confirmation entirely on every order after the first (graph.ts:39–46).

② The final gate once ignored its own reply and placed unconditionally — “caused a real ₹321 Paradise Biryani order to fire when STOP was sent. Never again.” (graph.ts:651–660). Both are now covered by smoke regressions.

05The 7-layer money-safety model

This is the heart of the project and the part most worth studying. Each layer is independent — the design assumption is that any single layer can fail and a real order still must not fire by accident. Verified against the code, not just the doc.

L1
Server kill switch — LB_REAL_ORDERS=1 required or every order is demo.
Checked inside the Placer via effectiveMode(). lib/user-prefs.ts:8. Worst case without it: “site exists, every order is demo, no money lost.”
L2
Per-user mode — user must individually opt into Live; default demo, 30-day Redis key. Switching pops a rose AlertDialog (“cannot be cancelled after they fire”).
Global switch always wins: effectiveMode = LB_REAL_ORDERS && mode:<phone>. lib/user-prefs.ts:27
L3
Three interrupt() gates — calorie, ETA, final. Each pauses the graph for explicit YES.
Non-YES re-prompts; STOP cancels. graph.ts:614–660
L4
30-second grace timer — after final YES, a STOP window before commit. awaitGrace polls every 750ms with a 5-failure circuit breaker that defaults to cancelled on Redis trouble.
“We’d rather waste your time than your ₹500.” lib/redis.ts:142–172. ⚠ Interactive STOP during this window is WhatsApp-only — see F1.
L5
Idempotency — sha256(userId · cartHash · dayUTC), 24h TTL, SETNX. Second identical order returns duplicate without firing; released on transient failure so a retry is safe.
lib/redis.ts:76–88, release wrapped in its own try/catch (audit B1#1).
L6
Per-user mutex — SETNX lock, 180s TTL (> the 60s function budget), compare-and-delete release. Concurrent inbound → fast UserBusyError.
TTL bumped 90→180s after the ₹321 race class. lib/redis.ts:119
L7
Abandoned-thread auto-clear — a paused gate older than 30min is force-STOP’d and the new message starts fresh.
Stops “waking up to find yesterday’s YES finished an order.” lib/agent/runner.ts:63–72

Supporting controls round it out: token redaction middleware strips Bearer ey… / JWT shapes from every log (lib/redact.ts), the WhatsApp webhook fails closed in production when its secret is unset (app/api/whatsapp/route.ts:24, verified live → 403), inbound messages are deduped by id (msg: key), and an order-value ceiling rejects carts ≥ ₹1000 to respect the Swiggy beta cap (graph.ts:369).

The doc is honest about what it does not protect: a compromised Swiggy MCP / MITM, clipboard theft between Claude Desktop and /connect, a malicious browser extension, and server-side key compromise (mitigation: rotate BYOC_ENCRYPTION_KEY, every user force-reconnects, ciphertexts become useless). docs/SAFETY.md §“What is not protected”.

Encryption posture

One env secret BYOC_ENCRYPTION_KEY (≥32 chars). Per-purpose subkeys via scrypt(secret, label) — distinct labels for the BYOC token, the session cookie, and the OAuth state blob — so rotating the env rotates all three in lockstep (lib/crypto.ts:21, lib/session.ts:18, lib/swiggy-oauth.ts:124).

  • Token envelope: base64(salt·iv·tag·ciphertext), AES-256-GCM (authenticated)
  • Session cookie lb_session: sealed {phone,expiresAt}, HttpOnly; Secure; SameSite=Lax, 30d
  • Decrypt failures are logged (byoc.decrypt-failed, session.decrypt-failed) so an accidental key rotation surfaces as a log flood, not a silent mass-logout
  • Token decrypted only inside SwiggyClient construction; never echoed, never returned to the client

LangGraph state is checkpointed in Neon Postgres per thread_id = phone, via a pg.Pool capped at 2 per lambda (Fluid Compute multiplies pools). The connection string must bypass PgBouncer — the transaction pooler breaks LangGraph’s prepared statements (lib/agent/checkpointer.ts:18–33). A daily Vercel cron sweeps checkpoints idle >7 days, carefully skipping threads with no heartbeat so it can’t race-delete a fresh one.

07Code-quality signals

What’s genuinely good

  • Typed error taxonomies at every boundary. SwiggyMcpError.kind (auth/rate-limit/not-found/address-stale/other) and IntentParseError.kind (timeout/rate-limit/config/schema/other) drive both user copy and log greppability. Word-boundary regex (\b401\b) so “4015 bytes” can’t trigger a token wipe.
  • Defensive parsing of a drifting upstream. Every Swiggy shape is parsed permissively and logs when the envelope is missing — so schema drift shows up as agent.parse.* instead of silent “no restaurants”.
  • Silent-failure discipline. Bare catch(()=>{}) was systematically replaced with safeLog; the audit doc enumerates all 18.
  • Request correlation. AsyncLocalStorage stamps every log with an 8-char request id + user id (lib/log-context.ts).
  • Comments explain why, citing real incidents — the ₹321 order, the gate-leak reducer, the PgBouncer break, the setup-promise poison.

Texture & conventions

  • Strict TS, Zod at every trust boundary (intent, cart, interrupt payloads as a discriminated union).
  • Clean separation: lib/agent (brain), lib/mcp (I/O), lib/* (primitives), routes are thin.
  • Graceful degradation: persona LLM optional (heuristic kcal fallback), Postgres optional (MemorySaver), Redis offline shim for smoke.
  • PostgresSaver.setup() rejection clears its cached promise so one bad cold-start can’t poison the lambda forever.
  • Local secrets (.env*, .admin-secret.local, .swiggy-oauth-client.json) are git-ignored — none are tracked.

Overall: the failure-handling is the most mature thing in the repo. Most “AI agent” side-projects swallow errors and pray; this one classifies, logs, and tests them.

08Findings & risks

Calibrated against the project’s own bar. Nothing here is a live money-loss bug today — the two-layer kill switch keeps the deployed site in demo — but several are real gaps between the marketed behavior and the shipped behavior, and a couple are latent the day someone flips LB_REAL_ORDERS=1.

MEDIUMF1 · The “visible 30-second countdown, type STOP to cancel” is WhatsApp-only

The marketing promise — hero “waits 30 seconds before committing”, how-it-works “visible countdown after the final YES. Reply STOP to cancel”, FAQ “a visible 30-second window where typing STOP cancels”, and docs/SAFETY.md L4 — is only fully true on the unprovisioned WhatsApp channel.

Why. Only app/api/whatsapp/route.ts:90 checks isGraceActive() before acquiring the lock, so a WhatsApp STOP can call cancelGrace() mid-window. On the web surface: (a) there is no client-side countdown component in app/order/new/page.tsx (the graceSeconds in the interrupt payload is plumbed to the client but unused); and (b) after the final YES the Placer blocks ~30s inside awaitGrace() while holding the per-user lock. A web STOP during that window hits /api/chat → acquireUserLock fails → UserBusyError → 429 “finishing your previous message.” The UI just shows “Working on it…” with the input disabled.

Net. On web, the final layer of the headline regret-prevention feature is a non-interactive server delay. STOP works at every gate including the final prompt — but not in the 30s after the final YES. cancelGrace/isGraceActive are referenced nowhere outside the WhatsApp route.

latent unless LB_REAL_ORDERS=1 Fix: add an isGraceActive pre-lock check + a cancel endpoint to the web path, and render the countdown the payload already carries — or soften the copy to “a 30s delay” for web.

LOWF2 · README states the wrong intent model

README.md:54 and the stack table README.md:88 say intent extraction is Groq llama-3.1-8b-instant. The code defaults to openai/gpt-oss-20b (lib/agent/intent.ts:53) — and the CHANGELOG documents why they switched (Llama models reject AI-SDK v6’s json_schema response format). docs/ARCHITECTURE.md:232 is correct; the README simply wasn’t updated after the fix.

LOWF3 · “signature verification” overstates the webhook control

README.md:136 says the WhatsApp webhook has “signature verification.” It’s actually a shared-secret compare against a header or ?secret= query param (app/api/whatsapp/route.ts:24–37) — there is no HMAC over the payload, and parseInbound does no cryptographic check. SAFETY.md gets this right (“webhook secret”); only the README term is inflated. The query-param fallback also risks the secret landing in access logs/referrers.

LOWF4 · Dead / misleading config in .env.example
  • LASTBITE_AGENT_MODEL — declared and even given a default; nothing reads it. The real knob is LASTBITE_INTENT_MODEL.
  • SKIP_TOKEN_VALIDATION — comment claims it “bypasses the live Swiggy MCP token-validation probe,” but no code consumes it; app/api/oauth/byoc/route.ts always calls SwiggyClient.validate(). The documented escape hatch doesn’t exist.

Both verified by source grep. Harmless at runtime, but config that lies is a debugging trap.

LOWF5 · SAFETY.md slightly overstates upstream idempotency

The money-invariants table implies “idempotency upstream is also Swiggy-side.” The Placer comment is more honest: “idempotency_key isn’t part of the schema — server-side dedup is governed by Swiggy” (graph.ts:704–708). In practice the dedup guarantee is local (the idem: key + the 180s mutex); whether Swiggy dedups a repeated place_food_order is an assumption, not something Last Bite controls. The local controls are sound; just don’t lean on a Swiggy-side guarantee in the contract.

MINORF6 · A personal phone number is hardcoded in a script that hits prod

scripts/live-e2e.ts:45 returns +916304362869 as a fallback and drives the production /api/admin/run-turn endpoint. Fine for the author’s own loop, but it’s a real number committed to a public repo and a script that places real turns against prod.

MINORF7 · Non-constant-time secret compares; XFF-trusting rate-limit key

Admin and webhook secrets compare with !== (app/api/admin/*, app/api/whatsapp/route.ts) rather than a timing-safe equal — negligible against high-entropy secrets, but trivial to harden. The connect rate-limiter keys on the first x-forwarded-for hop (lib/ratelimit.ts:26); on Vercel the platform sets XFF, but it’s worth being explicit that the key is only as trustworthy as the proxy chain.

Calibration. F2–F7 are the kind of small drift that accumulates in a fast-moving solo build; the project’s own audit caught 18 deeper issues, so the bar here is high. F1 is the one worth fixing before the “30-second STOP” line goes in front of a non-WhatsApp user.

09Tests & verification

scripts/smoke.ts is a dependency-free regression harness: in-memory Redis, fixture MCP, persona skipped, 1-second grace. It exits non-zero on any deviation. Eight scenarios — and notably, the two that exist because of real bugs:

Coverage shape. Excellent on the state machine and safety invariants. The gaps are the usual ones for this stage: no test exercises the real parseIntent path (LLM is stubbed), no HTTP-route tests (auth, rate-limit, fail-closed webhook — those are verified manually / live per the docs), and the web-surface grace behavior in F1 isn’t asserted (scenario 2 takes the webhook path). There’s no CI config in the repo, so the smoke run is manual (npm run smoke). Live scripts (live-e2e, capture-real-fixtures, real-mcp-probe, snapshot-cart) hit real Swiggy and deliberately never call place_food_order to avoid charges.

10Maturity signals

Honest copy pass

Compliance posture

Anonymous-by-default, 30-day TTLs, redaction, a live /privacy page worded as “aligned with the principles of DPDP” — and the audit explicitly defers the stronger “DPDP-grade” claim until a grievance officer / Data Fiduciary exists.

Brand discipline

11Portfolio framing

Read as a portfolio artifact, this is strong precisely because it’s narrow. It demonstrates the skills an agentic-commerce / applied-AI role actually screens for:

  • Human-in-the-loop agent design with LangGraph interrupt(), not a chat wrapper.
  • Spending-money safety as a first-class, layered, tested concern.
  • MCP integration against a real, drifting, beta third-party server — with fixtures captured from the live tool.
  • Deterministic-where-it-matters judgment: LLM for intent only, TS for everything that affects an order.
  • Production operability: typed errors, redaction, request ids, runbook, cron GC.
  • Calibrated communication: the audit + honest-copy pass are unusually self-aware.
  • Constraint navigation: turned an upstream whitelist blocker into a documented BYOC bridge instead of faking access.

The CLAUDE.md five-project arc shows intent to compound (~60% reuse per project), but only Project 1 exists — judge it as one deep project, not a portfolio of five.

BMethod & caveats

This analysis read the full agent core, all lib/ primitives, every API route, the safety/architecture/audit/changelog docs, the smoke harness, the env contract and Vercel config directly; frontend pages, scripts and remaining docs were summarized via an exploration pass. Every finding cites a verified file:line; the dead-config and model-drift claims were confirmed by source grep. The codebase was not executed and no build/typecheck was run as part of this pass — assertions about runtime behavior (e.g. F1’s lock/grace interaction) are derived from reading the control flow, not from a live repro. Severities are calibrated to the project’s own standard, which is high.
